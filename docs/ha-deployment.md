# Three-zone deployment and recovery

The repository now contains the deployment mechanisms and local failure proofs. Production credentials, DNS and physical zones remain properties of the target environment. The local kind lab has three labelled worker containers; it does not create three independent availability zones.

## AWS foundation

`infra/ha/eks.cloudformation.json`, generated by `python -m scripts.render_eks`, creates a VPC with three public/private subnet pairs in separate available zones, a NAT gateway per zone, private EKS workers, encrypted disks, KMS protection for Kubernetes secrets, a managed control plane, an explicit administrator access entry, and EBS CSI with Pod Identity. Three node groups keep at least one worker in each zone. The template requires an existing administrator role and a restricted API administrator CIDR. It enables audit logs and retains the cluster and KMS key on stack deletion. It creates billable compute, storage, NAT and control-plane resources; it has not been launched by the local rehearsal.

Use `ap-south-1` for the primary deployment and a separately administered `ap-southeast-1` backup repository when those regions satisfy your requirements. Validate account permissions and quotas first. Example commissioning command, with actual account-specific values:

```sh
aws cloudformation deploy --region ap-south-1 --stack-name aegis-prod \
  --template-file infra/ha/eks.cloudformation.json --capabilities CAPABILITY_IAM \
  --parameter-overrides AdminCidr=<administrator-ip/32> AdminPrincipalArn=<administrator-role-arn>
aws eks update-kubeconfig --region ap-south-1 --name aegis-prod --alias aegis-production
```

Check real node `providerID`, EC2 availability-zone placement and node readiness before calling the result multi-zone. Use a separate kubeconfig/context for every recovery environment. Avoid changing cluster deletion protection or deleting retained volumes as part of routine operation.

## Commission PostgreSQL and message quorum

1. Install the pinned operator: `kubectl --context aegis-production apply --server-side -f https://github.com/cloudnative-pg/cloudnative-pg/releases/download/v1.30.1/cnpg-1.30.1.yaml`. Wait for its controller deployment, then apply `infra/ha/operator-ha-patch.yaml` using `kubectl patch deployment cnpg-controller-manager -n cnpg-system --type merge --patch-file ...`.
2. Install cert-manager from `https://github.com/cert-manager/cert-manager/releases/download/v1.21.3/cert-manager.yaml` and wait for its controllers/webhook. Install the Barman plugin from `https://github.com/cloudnative-pg/plugin-barman-cloud/releases/download/v0.16.0/manifest.yaml` in `cnpg-system`. These versions are compatible; the plugin requires CloudNativePG 1.30+.
3. On EKS, apply `infra/ha/storage.yaml` and verify the CSI driver. Ensure another default StorageClass does not override the intended class. For an existing non-EKS cluster, use its encrypted, zone-aware CSI class instead. Do not apply the EBS class to kind.
4. Apply `infra/ha/postgres.yaml`. Wait for three ready instances. Synchronous commits require one standby, failover quorum is enabled, and isolation checks are enabled. The operator controls promotion and the stable `aegis-pg-rw` service. Do not manually override a failed failover quorum. Required zone anti-affinity keeps database copies in separate zones.
5. Export a strong `SESSION_SECRET` and run `python -m scripts.create_ha_secrets <private-output.json>`. Preserve the generated audit public key independently and the private bootstrap file securely. Apply it only to the intended namespace/context. The helper refuses overwriting a previous file. No S3 credentials are present in this runtime secret.
6. Apply `infra/ha/nats.yaml`. Wait for `Certificate/aegis-nats` and the three NATS pods. Client and route traffic use TLS; routes require mutual certificate validation and distinct route credentials. JetStream requires three replicas. A pre-existing weaker stream causes the production worker to fail rather than silently accept weaker durability. Migrate its replica configuration explicitly with the supported NATS tooling before resuming.

## Workloads, TLS and ingress

Build and publish the API (`infra/Dockerfile`), gateway (`infra/Realtime.Dockerfile`) and frontend (`infra/Web.Dockerfile`) to an authorized registry. Resolve their image digests. The renderer rejects mutable tags and non-HTTPS origins:

```sh
python -m scripts.render_ha --api-image <registry/api@sha256:digest> \
  --gateway-image <registry/gateway@sha256:digest> \
  --web-image <registry/web@sha256:digest> --origin https://<owned-domain> \
  --output <new-manifest.json>
kubectl --context aegis-production apply --dry-run=server -f <new-manifest.json>
```

Install an ingress-nginx controller with `infra/ha/ingress-values.yaml`, the appropriate cloud load-balancer integration and a valid `aegis-public-tls` certificate in namespace `aegis`. Point the owned domain to that load balancer. Install metrics-server for CPU autoscaling. Restrict the load balancer's backend access to the ingress controller; application services remain ClusterIP-only. Internal ingress routes `/v1/live/` to the Go gateway, `/v1/` to API replicas, and `/` to static web replicas.

Apply the migration Job from the rendered List first and wait for completion before applying the remaining workloads. Give a new migration job a release-specific name on subsequent upgrades; Kubernetes Job templates are immutable. The current migration is idempotent. Provision actual user accounts through an authorized account-management procedure; do not publish classroom demo passwords.

The workloads use read-only filesystems, bounded connection pools, no service-account token mounts and default-deny network policies. API readiness checks the database; liveness checks only its process. Worker/relay readiness uses an actual successful loop heartbeat. API verifies the explicit HTTPS public origin and sets secure cookies in production. Forwarded headers are trusted only inside the network boundary enforced by the ingress/network policies.

Stateless replicas spread across available zones and may rebalance over two healthy zones after a failure. Database/NATS replicas retain strict independent-zone placement: after one zone is lost, two surviving copies maintain quorum while the third recovers. A further loss can deliberately stop progress. Increase gateway capacity before a scheduled close; reactive CPU autoscaling does not guarantee advance capacity. Per-user quotas are per gateway process; add an edge-wide identity quota if your anti-abuse policy requires a fleet-wide cap. Prometheus must scrape every gateway replica, using Kubernetes pod discovery or ServiceMonitors rather than a single load-balanced scrape target.

## Continuous independent recovery

Provision the protected bucket using `infra/offsite/bucket.cloudformation.json` in the independent backup domain. Create namespace secret `aegis-backup-writer` containing `ACCESS_KEY_ID` and `ACCESS_SECRET_KEY` from a dedicated backup writer principal, using `infra/ha/barman-writer-policy.json` with the actual bucket name. An IAM workload identity can replace static keys when configured by your cluster administrator. API, gateway, web and worker pods never mount this secret.

Replace `REPLACE_INDEPENDENT_BUCKET` in `infra/ha/backup.yaml`, then apply the ObjectStore and patch `Cluster/aegis-pg` with `infra/ha/backup-patch.yaml`. This activates continuous WAL shipping to the remote object repository. Apply the ScheduledBackup after the plugin and archive condition are healthy. Confirm an actual completed physical backup plus recent successful WAL archival before recording recovery coverage. Do not configure Barman automatic deletion against a COMPLIANCE-locked repository; make retention changes through the independent backup administrator after verifying recovery chains.

`infra/ha/recover-cluster.yaml` restores a **new** three-instance cluster to an explicit timestamp through the Barman plugin. It never changes the existing application service or database secret. Verify ledger anchors, pending-request reconciliation, winner reconstruction, protected checkpoint, data-loss exceptions and full recovery duration before an operator changes the application authority. Keep the original authority fenced before rerouting. Back up Bacula Catalog/configuration, offsite receipts and decryption/signing keys in independently recoverable locations.

## Reproduce the node-loss proof

Install local tools with `python -m scripts.install_ha_tools`. The checksummed tools go only in ignored `.tools/`. Create the lab with `.tools/kind create cluster --name aegis-ha-lab --config infra/ha/kind.yaml --kubeconfig .tools/ha-kubeconfig` (use `.exe` on Windows). Apply the operator, operator HA patch and PostgreSQL manifest using this kubeconfig. Then run `python -m scripts.rehearse_ha` (Linux: add `--kubectl .tools/kubectl`).

The harness insists on the disposable context and worker names. It uses real engine transactions, saves independent ledger evidence, stops the primary's Docker worker node, checks that node is fenced, waits for operator promotion, verifies all committed decisions and allocation, retries old request IDs, rejects a stale worker epoch, and restarts the original node afterward. It never performs this fault against a production context. `docs/evidence/ha-local.json` records the measured result. The same drill is a dedicated GitHub Actions workflow.
