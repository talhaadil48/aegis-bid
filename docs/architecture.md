# Implemented consistency policy

PostgreSQL is the only decision authority. The public Go ingress groups individual authenticated HTTP requests into internal batches of at most 512, with a 100 ms collection ceiling and at most eight in-flight batches per auction. FastAPI verifies each real session, bidder role, UUID and integer-cent amount; the internal endpoint requires an independent service key. Public callers cannot supply their own identity. A direct FastAPI admission route remains available.

SQL admission reserves sequence ranges under a short per-auction reservation lock, then holds a shared transaction advisory lock while inserting the batch. Different batches can insert concurrently. The database generates admission timestamps; sequence gaps from retries/rollbacks are allowed, while decision order remains strictly increasing. Globally sorted request-UUID advisory locks protect immutable payload bindings across auctions. A stable UUID binds one bidder/auction/amount tuple; changed payloads return a conflict. The 60,000-pending limit uses a processed watermark fast path and an exclusive, exact count near capacity.

Workers first take an exclusive intake barrier to wait for earlier admission transactions, lock the auction before its lease, and capture the first pending sequence prefix. They release the barrier before evaluating and committing the batch, permitting later admissions to continue. The auction row lock serializes decisions; the barrier prevents an uncommitted lower sequence from being overtaken. A five-second lease and a new holder identity on every boot fence stale workers with an incrementing epoch.

Each transaction commits at most 512 separate decisions, request states, offers and SHA-256-linked events. One outbox notification identifies the latest committed batch version; individual audit events are retained. The processed watermark advances in the same transaction. A crash before commit rolls the whole batch back; redelivery after commit reuses its final states and unique decision keys.

Admission atomically inserts a separate `command_queue` publication receipt. Relay acknowledgment updates that relation without locking live queued business rows. JetStream is a durable wake-up journal; workers also reconcile SQL pending records, so restore does not depend on exact cross-system snapshot alignment. QUEUED proves committed SQL intake, not a broker quorum acknowledgment. Notifications are eventually delivered and may duplicate. The Go live gateway currently polls one authenticated snapshot per active auction per second and uses bounded prepared-frame fanout; it does not consume outbox subjects or decide bids.

Strict global increments apply: the next eligible amount is max(reserve, highest current offer + increment). At most one same-price concurrent bid succeeds. Distinct current bidders are ranked by amount descending then decision sequence ascending. Allocation happens only after the server deadline and draining queued commands. Admission before the deadline remains eligible even when processed later. Manual close moves the deadline under the auction lock; it does not discard already admitted requests.

Valid new requests after the deadline or final close receive a terminal CLOSED admission receipt in `admission_outcomes`. They do not append to the sealed bid ledger or alter winners. Same-payload retries retain their original accepted/rejected result. Reconciliation repairs legacy queued rows on already closed auctions. HTTP 202 means pending; HTTP 200 means a terminal outcome.

PostgreSQL row locks serialize a hot auction. Independent auctions may process concurrently. The distinct-bidder harness records client writes, SQL admission timestamps, accepted/rejected/queued counts, drain time and independently signed replay. See [measurements](measurements.md) for actual capacity, profile and failure scope. Admission during the final ten seconds does not imply all decisions finish before the deadline, nor that transaction commit visibility was measured at the admission timestamp. One-host results do not establish physical multi-zone resilience.

Reference semantics: [PostgreSQL row locks](https://www.postgresql.org/docs/18/explicit-locking.html), [JetStream at-least-once delivery](https://docs.nats.io/concepts/jetstream).
